# 新解释器架构：从 AST 执行到分层 IR

MATLAB 解释器需要同时面对两类需求：普通计算代码需要清晰的数据流和优化空间，`eval`、动态 workspace 与路径变化又要求执行器保留完整的动态语义。

这次设计的思路是：**以 Non-SSA 提供语义基线，让常见路径进入 SSA 和优化执行；当运行时假设失效时，恢复状态并回到基线继续执行。**

本次分享定位为方案推演与设计取舍，分三部分介绍设计动机、各层 IR 的责任，以及支撑这套架构的复用和回退机制。以下描述的是目标设计，当前已实现部分 M 语法到 Non-SSA 的构建及文件缓存，SSA、优化执行与 JIT 尚未实现。

## 一、设计背景：为什么需要分层 IR

### 1. AST 适合表达语法，但执行与优化需要更明确的结构

直接遍历 AST 是建立解释器的一条自然路线。赋值、表达式、分支和循环都有对应节点，执行器按照语法结构递归求值。

随着优化需求增加，这种组织方式会遇到几个困难：

| 问题 | 对后续设计的影响 |
| --- | --- |
| 求值顺序、临时结果和跳转隐含在节点解释函数中 | 难以统一分析、调整执行过程 |
| 变量的定义和使用关系不够直接 | 常量传播、死代码消除等需要反复推导数据流 |
| 节点执行同时承担动态语义和优化逻辑 | 优化越来越依赖具体语法节点，维护成本增加 |
| 解释执行与 JIT 都从 AST 出发 | 容易重复实现控制流转换和语义处理 |

引入 IR，就是把这些执行步骤显式表达出来：复杂表达式拆成指令，分支和循环表示为基本块与跳转，计算结果成为明确的值。执行器和优化 pass 因而可以围绕同一套执行结构工作。

这里的目标是建立可分析、可变换的基础。具体性能收益仍取决于指令设计、运行时实现和实际测量。

### 2. MATLAB 的困难：变量状态和调用目标都可能变化

#### 变量可以在显式赋值之外被修改

`eval` 执行运行时确定的代码；`evalin`、`assignin` 还能按名字访问其他 workspace。变量的值和类型，可能在当前函数没有赋值语句的地方发生变化。

```matlab
function y = outer()
    x = 1;
    changeCaller();
    y = x;
end

function changeCaller()
    assignin('caller', 'x', 'changed');
end
```

`outer` 中没有第二次给 `x` 赋值，但调用结束后，`x` 已经从数值变成了字符数组。分析当前函数的赋值语句，不足以确定调用之后的变量状态。

动态 workspace 还涉及变量是否绑定、按名字读取时应看到什么，以及允许动态创建变量时如何处理新名字。有静态 workspace 限制的场景，则需遵守相应规则。

#### 运行环境可以改变函数分派

`cd`、`addpath`、`rmpath` 可以改变当前目录和搜索路径。对于依赖这些环境解析的调用，同一个函数名可能对应不同实现。按参数类型选择的方法，还依赖实际参数的类型。

因此，编译时确定的调用目标，需要明确它依赖哪些条件。局部函数、嵌套函数、函数句柄和路径查找各有自己的规则，不能统一视为固定目标。

#### 两种动态性会相互影响

```text
变量的值和类型
    ↓ 影响
函数分派
    ↓ 决定
被调用代码对 workspace 和路径的影响
    ↓ 改变
后续变量状态与函数分派
```

调用目标不确定，就难以分析它会怎样修改变量；变量类型不确定，又可能使调用目标无法确定。要求在执行前精确分析任意程序，会让大量结果退化为“未知”，限制可用的优化。

### 3. SSA 的价值，以及它在这里遇到的核心问题

SSA（静态单赋值形式）让每个值只有一个定义。源码变量的多次赋值，对应不同的 SSA 值：

```text
源码：                  SSA 示意：
x = 1;                 x1 = 1
x = x + 2;             x2 = add x1, 2
y = x;                 y1 = x2
```

分支和循环的合流由 phi 等机制表达。定义和使用关系明确之后，常量传播、死代码消除、类型分析和后续特化都能在统一的数据流上进行。

**SSA 值仍然可以保存动态类型对象。** SSA 首先明确值的来源，并不要求编译时已经知道每个值的类型。

MATLAB 在这里的核心困难，是动态操作可能绕过显式定义，改变源码变量的当前绑定：

```text
x1 = 1
call changeCaller
use x1                 // 此时 x1 已不能代表源码变量 x 的当前值
```

`x1` 本身仍然是原来的值，但“变量 x 当前对应 x1”这个关系已经失效。即使动态代码只读取 workspace，也必须能读到当前 SSA 值，不能读到尚未同步的旧存储。

因此，SSA 转换之外还需要解决两个问题：**如何让动态操作观察正确的变量状态，以及对应关系失效后如何继续执行。** 这正是语义基线和回退机制要承担的责任。共享变量、闭包、`global` 和 `persistent` 等状态也需要单独建模，不能默认全部提升为独立 SSA 值。

### 4. 为什么不把“提前证明没有 eval”作为前提

要判断执行期间是否会触发动态 workspace 操作，需要沿调用关系分析，不能只扫描当前函数里有没有 `eval`。把分析时机分成三个阶段，可以看到这条路线的边界。

| 分析阶段 | 已知信息 | 仍然存在的问题 |
| --- | --- | --- |
| 静态源码分析 | 源码、部分直接调用关系 | 环境和参数类型未知，部分调用目标无法确定 |
| 运行前分析 | 当前目录、搜索路径等运行环境 | 可以解析部分函数分派，但函数句柄入参等仍依赖实际输入 |
| 运行时分析 | 本次实参、实际句柄、当前环境 | 能逐步确定目标，但需要持续分析调用链并维护结论 |

运行前分析确实比单纯源码分析掌握更多信息。环境确定后，一部分函数分派可以解决，但下面这个函数仍然没有固定调用目标：

```matlab
function y = applyCallback(callback, x)
    y = callback(x);
end
```

仅凭源码和路径，无法知道调用者会传入哪个 `callback`，也就无法判断它是否间接执行动态 workspace 操作。

如果在每次调用前检查实际传入的句柄，分析就依赖本次实参，进入了运行时分析。继续要求提前证明后续调用链都没有 `eval`，还要跟踪更多句柄、环境变化和动态生成的代码，最终形成持续维护的分析机制。

由此得到的设计选择是：静态和运行前分析可以辅助优化，但常见代码进入 SSA 不以这份证明为前提。**先在明确假设下执行，实际遇到破坏假设的动态行为时，再由运行时机制处理。**

## 二、架构思路：每层 IR 各自解决一个问题

### 1. 整体流程

```text
AST → Non-SSA → based SSA → optimized SSA → MLIR → LLVM IR → native code
                └──────── SSA 阶段 ────────┘   └──────── JIT 阶段 ────────┘
```

Non-SSA、based SSA 和 optimized SSA 都可以解释执行。JIT 在 SSA 的基础上继续生成机器码。

| 层次 | 主要责任 |
| --- | --- |
| AST | 表达源码的语法结构 |
| Non-SSA | 用 slot 和 load/store 建立完整的语义基线 |
| based SSA | 将大部分 slot 访问转换为寄存器值之间的数据流 |
| optimized SSA | 在可检查的函数行为假设下进一步优化 |
| MLIR → LLVM IR → native code | 逐步降低表示，完成 JIT 编译 |

### 2. Non-SSA：保存变量语义，提供执行基线

Non-SSA 引入 **slot** 表示源码中能够确定的具名变量，用 `load` 读取变量，用 `store` 写入变量：

```matlab
x = 1;
x = x + 2;
y = x;
```

```text
store slot_x, 1
r1 = load slot_x
r2 = add r1, 2
store slot_x, r2
r3 = load slot_x
store slot_y, r3
```

临时寄存器表示计算结果，slot 表示源码变量的当前绑定。同一个变量可以多次赋值，对应同一个 slot 的多次写入。

这一层承担完整的动态语义。按名字访问已有变量时，要与 slot 状态保持一致；运行时产生的新名字，则由动态 workspace 配合处理。即使某种语法暂时无法 SSA 化，也应该能在 Non-SSA 中执行。

**Non-SSA 既是 SSA 转换的起点，也是回退后继续执行的落点。**

### 3. based SSA：假设没有动态 workspace 操作，让值流直接化

构建 based SSA 时，先按不存在 `eval`、`evalin`、`assignin` 等动态 workspace 操作的情况处理，不要求提前证明整个调用链都满足这个条件。

在这一假设下，大部分 slot 的 load/store 可以消除，变量使用直接引用寄存器值。前面的例子变为：

```text
x1 = 1
x2 = add x1, 2
// 后续对 y 的使用直接引用 x2
```

这里先完成变量访问到 SSA 值流的转换；常量折叠等进一步优化放在下一层。需要共享或有特殊语义的状态，仍保留相应的访问机制。

实际运行遇到破坏假设的操作时，就恢复状态，切换到 Non-SSA 解释执行。例如，当前函数执行 `eval`，应在执行它之前回退；callee 改写 caller 的变量，则要在对应的调用边界恢复 caller。

### 4. optimized SSA：在函数行为假设下优化，执行前检查条件

常量折叠除了需要常量输入，还依赖对应函数的行为。如果用户自定义了相关函数，原先按已知函数行为计算出的结果就可能不再正确。

因此，optimized SSA 增加一层环境假设：**优化所依赖的函数，没有被用户自定义实现替代。** 优化 pass 使用这个条件时，需要记录相应函数依赖。

```text
based SSA
    ↓ 按相关函数未被用户自定义的假设优化
optimized SSA + 函数依赖
    ↓ 解释执行前检查当前环境
    ├─ 满足条件 → 解释执行 optimized SSA
    └─ 条件不满足 → 选择仍然有效的执行层
```

检查范围是优化实际依赖的函数。环境中存在其他自定义函数，并不意味着整个优化版本都不能使用。

两层 SSA 的区别也在这里：

| 层次 | 主要假设 | 对应机制 |
| --- | --- | --- |
| based SSA | 动态 workspace 操作不破坏变量与 SSA 值的对应关系 | 实际遇到相关行为时恢复状态，回退 Non-SSA |
| optimized SSA | 环境满足优化所依赖的函数行为条件 | 执行前检查依赖，不满足时停用该优化版本 |

执行期间环境继续变化的问题，通过引入**世界计数（world counter）**处理：影响函数分派的路径、当前目录等环境发生变化时，更新世界计数；执行前验证优化条件时，记下验证所对应的计数。

运行时在必要的检查边界比较计数。如果计数未变，可以沿用已验证的结论；如果计数变化，则重新检查相关优化依赖。计数变化只说明环境发生了更新，不一定表示该优化版本已经失效；重新检查不通过时，停止使用相应优化结果，转入仍然有效的执行路径。

检查必须发生在继续使用受影响的优化结果之前。哪些环境操作更新计数、在哪些边界检查，以及失效后如何衔接执行，留待后续分享展开。

### 5. JIT：沿用 SSA 的结果继续编译

```text
optimized SSA → MLIR → LLVM IR → native code
```

MLIR 承接语言侧 SSA 的结果，继续降低到 LLVM IR，再生成本机机器码。语言语义、变量访问和解释执行的分层已经在前面建立，JIT 可以在此基础上继续推进。

本次分享只明确这条路线。MLIR 方言、类型特化、运行时接口和机器码回退机制，留待 JIT 设计展开。

## 三、关键机制：复用 IR，并让回退尽量便宜

### 1. 三个版本长期保存，共用函数信息

一个 M 函数保存 Non-SSA、based SSA 和 optimized SSA 三种版本，可以按需构建并缓存。在源码不变、相关依赖有效的情况下，每种版本理论上只需构建一次，无需每次调用重新生成。

三个版本描述同一个函数，变量和 slot 的身份保持一致，主要区别在指令、控制流和值的表示：

```text
M 函数
├── 公共信息：变量名称、slot 身份和属性
├── Non-SSA：基本块、指令、值表
├── based SSA：基本块、指令、值表
└── optimized SSA：基本块、指令、值表、优化依赖
```

SSA 消除 load/store 后，仍保留 slot 的身份，以便将寄存器值恢复到对应变量。各阶段的寄存器编号和值表则可以不同。

解释执行也尽量复用动态对象表示、指令执行逻辑、调用和异常处理机制。每次调用的寄存器值、slot 值和执行位置属于独立执行帧；函数描述可以共享，递归调用的当前状态必须分开。

### 2. 区分源码失效与优化条件不满足

| 检查对象 | 检查内容 | 影响 |
| --- | --- | --- |
| 源码版本 | 按需检查源文件时间戳和缓存版本 | 源码变化后，三种 IR 一起失效并重新构建 |
| 优化依赖 | 执行前检查相关函数是否被用户自定义；执行期间通过世界计数变化触发重新检查 | 条件不满足时，不能继续使用对应 optimized SSA |

环境条件不满足，不代表 Non-SSA 和 based SSA 也需要因源码变化而重建。缓存与版本的组织细节见 [Baltam IR 组织与缓存设计](IR组织与缓存设计.md)。

### 3. 回退的核心：让 Non-SSA 从当前状态继续

SSA 执行建立在一定假设上。当运行时遇到 `eval` 等动态 workspace 操作，无法继续维持这些假设时，就切换到 Non-SSA 解释执行。

回退需要回答两个问题：

```text
回退描述
├── 执行位置：回到哪条 Non-SSA 指令继续
└── 变量状态：当前每个 slot 绑定到哪个寄存器值
```

执行位置决定程序从哪里继续；slot 与寄存器值的映射，则让 Non-SSA 能恢复出源码变量的当前状态。两者配合，才能接着已经完成的工作执行，避免重复调用或丢失变量修改。

### 4. 开销思路：少记录，按需恢复

回退预计很少发生，因此不希望普通执行路径为了回退，反复复制完整的变量状态。

基本思路是保存恢复所需的描述，例如 `slot_x → r7`，在真正回退时再恢复对应的值。相邻位置的映射可以共享相同部分，仅记录变化，并结合检查点减少元数据开销。

本次先明确这个取舍：**让常见路径保持轻量，把更多恢复工作留到低概率的回退发生时。** 回退边界、分支和循环中的映射、优化后的状态维护等细节，留待下一次分享。

已有讨论见 [SSA 到 non-SSA 的运行时 Deopt 设计思路](SSA到非SSA的运行时回退设计.md)。
