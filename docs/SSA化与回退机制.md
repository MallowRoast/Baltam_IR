# SSA 化与回退机制

本文说明影响 SSA 变量定义的情况、回退所需信息及对 IR 的影响。运行时部分是设计约定，尚未实现。

## 第一部分：哪些情况会影响 SSA 中的变量定义

| 情况 | 处理方式 |
| --- | --- |
| 函数内部可静态保护的 eval/load 调用 | 使用工作区屏障，调用后继续 SSA |
| 子函数、函数句柄、feval 等调用修改父工作区 | 在实际修改时检测，必要时让目标帧回退到 Non-SSA |
| clear/clearvars 解除变量绑定 | 由内置函数运行时实现使当前赋值绑定失效，变量读取检查有效性 |
| 全局、持久及嵌套函数共享变量 | 保留 slot 和 load/store，不做普通局部变量提升 |

### 1. eval/load 与工作区屏障

对于可建立保护的工作区调用：

```text
call builtin.load(%file)
workspace_barrier
%new_x = load slot_x
```

屏障使变量与旧 SSA 定义之间的当前绑定结论失效。之后第一次读取重新取得工作区状态；如果先发生赋值，则直接使用新定义。已经产生的 SSA 值保持不变。

源码出现 eval/load 名称，不代表实际目标一定是内置函数。保护必须结合实际分派及影响范围，不能仅按名字执行内置语义。

IR 不设置显式工作区同步指令。运行时必须保证工作区访问取得最新变量状态；如何通过来源表访问、何时物化及如何兼容旧接口，留待运行时实现时设计。

### 2. 动态调用与回退

回退触发条件是：**子函数实际修改了父函数工作区中已提升的变量，且没有对应的工作区屏障保护。** 尤其需要关注嵌套函数中的动态工作区操作。

普通调用本身不触发回退，源码存在 eval 等操作也不意味着立即回退。通过保留的共享 slot 修改变量，或在已有屏障保护下修改变量，可以继续 SSA。

运行时定位的是操作实际访问的工作区所属帧。词法父环境不一定是当前调用者，不能仅按固定栈层数选择回退目标。影响范围无法精确判断时，可以保守标记目标 SSA 帧回退。

### 3. clear/clearvars 与绑定失效

实际执行内置 clear/clearvars 时，通过来源表找到被清除变量的当前赋值：

```text
slot_y → %y1
```

使这次赋值绑定失效，解除真实工作区绑定，并删除旧来源记录，避免以后恢复旧值。状态保存在当前执行帧中，不修改静态 Value，也不销毁旧寄存器数据。

后续变量读取需要检查对应绑定是否有效；已经取得的其他变量值、中间结果和实参不受追溯影响。重新给 y 赋值会建立新的有效绑定，旧绑定不会因此恢复有效。循环中再次执行赋值也需建立本次状态。

这条路径处理解除绑定；未经保护的跨帧工作区修改仍按回退协议处理。全局、持久和共享变量的清除规则由内置函数按实际存储语义执行。

### 4. 保留全局、持久和共享 slot

这些变量仍通过 slot 访问当前存储，不能跨可能修改该存储的操作复用旧 load。共享变量的拥有者和引用者都不提升；deopt 时沿用原存储绑定，不从旧寄存器回写。

从共享 slot 读取产生的 SSA 值只是该次读取的结果。若它作为历史中间结果仍需使用，仍按寄存器恢复规则保留。

## 第二部分：回退需要保留什么

回退依赖三类核心信息：

| 信息 | 保存与维护时机 | 用途 |
| --- | --- | --- |
| 每个可能触发回退的动态 SSA 指令执行完后，下一个 Non-SSA 指令的位置 | 克隆、SSA 构建时关联原指令；正常后继可由原指令推导 | 从原指令之后继续，不重放动态操作 |
| Non-SSA ValueId → SSA ValueId 的对应关系 | SSA 化时建立，随值替换和编号压缩更新 | 恢复继续执行所需的中间寄存器 |
| SlotId → 最新赋值 ValueId，以及绑定有效性 | 当前 SSA 执行帧在赋值、清除和工作区修改时维护 | 取得已提升局部变量的最新状态 |

寄存器映射允许多个 Non-SSA 编号对应同一个 SSA 值。实际回退时，再分析 Non-SSA 继续位置需要哪些寄存器并构建恢复计划，不提前为每个调用建立完整快照。

slot 来源表不覆盖所有中间寄存器。没有来源表项表示沿用真实 slot 状态，不一律表示 Undefined；未提升变量直接使用原存储绑定。

### 回退执行顺序

1. 实际访问父工作区时，保证被调用代码取得最新变量值和绑定状态；需要物化时由运行时完成。
2. 对满足触发条件的目标帧设置待回退标志，执行工作区修改，被调用代码继续运行。
3. 动态指令正常结束后，在执行下一条 SSA 指令之前检查标志。
4. 根据原指令定位 Non-SSA 继续位置，按需恢复中间寄存器；本次动态指令的结果直接填入对应的 Non-SSA 结果寄存器。
5. 切换到 Non-SSA，从原指令之后继续，后续原始 store 按正常顺序提交变量赋值。

已发生的工作区修改不能再被旧来源覆盖，调用和实参求值不能重放。异常退出若需要在目标帧继续执行，必须使用异常继续位置及相应恢复计划，不能使用普通的下一条指令。

### 来源表更新与分支、循环

来源表的逻辑结构是 `SlotId → ValueId`。SlotId 连续时可以使用数组和有效标记，容器形式留待运行时设计。ValueId 只标识静态定义；同一指令在循环中反复执行时，运行时还必须保留本次赋值的值引用或执行版本，不能让后续寄存器覆盖改变旧绑定。先完成右值求值，再在原赋值位置执行 record 更新来源；这两步之间不设置可观察的回退边界。求值或赋值失败时保留旧来源。

分支只有实际执行的赋值更新映射。例如两条路径分别将 x 赋为 `%x1` 和 `%x2`，执行帧自然记录本次路径的来源，不需要仅为回退插入 PHI。没有赋值的路径沿用旧绑定；此前未绑定则保持未绑定。循环覆盖同一 slot 的来源，表大小不随迭代次数增长。

动态创建的名字仍由工作区管理，不强行加入静态 SlotTable。内部迭代状态需要恢复，但不能作为用户变量暴露给工作区操作。

### 执行帧与重复访问

每次函数调用独立维护阶段版本、寄存器、工作区绑定、slot 来源表、暂停的动态指令、调用保护状态及 deopt_pending。递归调用不共享这些运行时状态，也不修改静态 ValueTable。

实际访问之前必须能取得最新变量状态；如需物化，应先完成物化再执行操作。同一暂停帧被多次访问时，后续访问必须看到已经发生的修改，不能反复将旧寄存器内容写回。来源表为空也不代表调用受保护，保护状态须单独记录。

物化方式、统一工作区接口和旧实现兼容留待运行时设计，不恢复显式同步指令。目标帧只在恢复执行边界切换阶段，本次调用回退后保持 Non-SSA。

### 跨阶段映射与基线生命周期

动态 SSA 指令保存原 Non-SSA 指令的非拥有引用，正常下一条指令由基线序列推导。FunctionUnit 已拥有各阶段版本，SSA 的 deopt_baseline 只保存非拥有指针；执行帧须保证所属模块及基线存活，基线在 SSA 使用期间不得修改或替换。

基线寄存器映射采用紧凑数组：

```cpp
// 下标为 Non-SSA ValueId，表项为对应的最终 SSA ValueId。
std::vector<std::optional<ValueId>> baseline_to_ssa;
```

克隆时初始化对应关系；replace_all_uses 记录 SSA 值替换，结束时解析替换链；compact_values 再通过重编号表更新来源。无需每次替换都遍历整张基线表。再次克隆时保留这些关系。

空项表示没有可用来源，不代表 Undefined。如果恢复需要该寄存器却没有来源，属于信息缺失，不能默默填充未定义值。

### 延迟构建恢复计划

首次实际回退时，在 Non-SSA 继续位置分析寄存器活跃性：

```text
LiveOut(I) = 所有后继 LiveIn 的并集
LiveIn(I)  = Use(I) ∪ (LiveOut(I) - Def(I))
```

正常返回分析原调用之后的 live-in。只在调用前使用、之后死亡的实参不必恢复；调用前已求值且后续仍需使用的中间结果需要保留，不能用变量修改后的当前值替代。

每个待恢复寄存器的来源分为两种：本次实际调用结果，或跨阶段映射指定的 SSA 寄存器。例如：

```text
Non-SSA %2 ← SSA %8
Non-SSA %4 ← SSA %11
Non-SSA %5 ← 本次调用结果[0]
```

计划只保存来源描述，不缓存某次执行的值或工作区快照。基线 CFG 和活跃性可按版本缓存；点位恢复计划按基线版本、SSA 版本、原指令身份及正常/异常边界区分，不能跨版本复用旧编号或指针。

延迟分析不等于延迟保留结果。优化必须提前保证潜在来源可读取；如果未来优化产生路径相关来源或需要重建表达式，应扩展恢复表示，不能任意选择一个 SSA 编号。

### 正常结果交付与异常恢复

返回边界先接收本次动态指令的实际结果，再检查 deopt_pending，随后才提交 SSA 赋值或进行回退。以 `x = dynamicFunction()` 为例，被调用代码对工作区的修改先发生，回退后由原 Non-SSA store 按正常顺序将返回结果赋给 x，不能提前执行 SSA 赋值记录。

恢复可先填入独立的 Non-SSA 寄存器数组，避免目标编号覆盖尚未读取的来源，成功后再提交阶段切换。ba_obj 沿用已有值复制与共享语义，无需因此深拷贝数组。

异常返回没有正常调用结果。若目标帧直接展开退出，保留工作区修改即可，不必恢复即将销毁的普通寄存器；若在帧内进入处理器继续执行，需要异常边的活跃状态、处理器状态及继续位置。完整异常控制流尚待实现，不能套用正常返回计划。

### 优化与寄存器分配边界

紧凑恢复映射和运行时来源表不挂入普通 Use 链，后续变换必须显式维护恢复用途。首版为每个 ValueId 保留独立运行时存储，不允许来源尚可被观察时复用该位置。即使帧还存活，错误的存储复用也会丢失结果。

之后可以独立建立 ValueId 到物理存储位置的映射，但生命周期计算须包含恢复用途。当前不涉及内联帧重建、JIT 装箱、机器寄存器物化或随循环增长的历史日志。

## 第三部分：对现在 IR 设计方案的影响

### 1. RecordInst 记录变量绑定

值定义与变量赋值分开表示，Value 不再保存 assigned_slot。已提升局部变量在原赋值位置执行：

```text
%0: double 1x1 = const !c0 (1)
record slot_a, %0
branch %condition, then, end
then:
    record slot_x, %0
    goto end
```

record 无结果，输入是普通 Use，静态保存目标 SlotId 与来源 ValueId。运行时只更新当前执行帧的绑定状态，不向全局、持久或共享存储写入，也不复制数组数据。未执行的分支不会更新绑定，不必仅为恢复变量状态额外插入 PHI。普通局部参数在入口同样生成 record，内部槽位不生成记录。

### 2. 优化保留 record 与恢复映射

值别名直接复用同一个 Value。普通替换同步更新 Use 和 Non-SSA 寄存器恢复来源。record 的来源随普通 Use 自动更新；多个 Non-SSA 寄存器和多个 slot 可以对应同一个 SSA 值。

record 提交可观察的赋值效果，不能因没有结果而直接删除，也不能随意提前、下沉或跨越可能失败的求值及工作区访问。它不依赖特殊 deopt Use；普通输入引用保证计算结果在提交绑定之前存活。

提交之后的存活由运行时绑定表保证。寄存器分配或循环重复执行不能破坏旧绑定，执行器需要保留赋值时的值引用或等效句柄。来源表与寄存器恢复映射承担不同职责，前者恢复变量，后者恢复继续执行所需的基线寄存器。

证明赋值在所有可观察使用前必然被覆盖，且不影响副作用、异常及恢复语义后，才可以消除对应 record。首版保守保留。

### 3. SSA 参数和返回值使用寄存器

参数由函数签名直接定义为 Value，直接作为普通参数变量的初始 SSA 值；返回指令直接引用当前路径的结果寄存器。签名保存参数的源码槽位关联和返回数量，SlotTable 仍用于工作区访问及回退，不再作为普通 SSA 参数和返回值的传递通道。

可提升参数在入口执行 record；需要保留存储的参数在入口建立实际 slot 绑定。多返回路径分别取得各自的结果，未定义输出保留对应读取语义。Non-SSA 继续使用原 slot 接口。

### 4. SlotInfo 保存声明属性和共享关系

已实现以下字段：

```cpp
class FunctionUnit;

struct SharedSlotRef {
    FunctionUnit* function;  // 最终拥有变量的词法外层函数，非拥有引用。
    SlotId slot;            // 目标函数 SlotTable 中的编号。
};

struct SlotInfo {
    InternedString name;
    bool has_global_decl = false;      // 存在全局声明。
    bool has_persistent_decl = false;  // 存在持久声明。
    bool shared_by_nested = false;     // 本函数拥有，且被嵌套函数共享。
    std::optional<SharedSlotRef> shared_target;  // 引用外层拥有的变量。
};
```

**声明存在不等于运行时已经建立对应绑定。** 例如 global 声明位于条件分支时，SlotInfo 记录声明存在，是否执行声明及实际绑定状态由运行时决定。GlobalDeclInst、PersistentDeclInst 的作用仍须保留，load/store 按实际绑定访问。

嵌套函数使用自己的 SlotId；shared_target 直接指向最终拥有者及其 SlotId，目标标记 shared_by_nested。同一槽位不同时设置这两种共享状态。静态函数身份只说明变量归属，具体存储由运行时词法环境定位到对应那次外层调用。

mem2reg 遇到上述任一声明或共享标记，都保守保留该 slot 的 load/store。这不意味着无条件将它绑定到全局或持久存储。

插入 GlobalDeclInst/PersistentDeclInst 时统一登记声明标记，因此 AST 构建、手动构造和文本读取都使用相同规则。标记保存在跨阶段共用的 SlotTable 中，不因某个阶段删除声明就自动清除。

共享关系通过 `inner.bind_shared_slot(inner_slot, owner, owner_slot)` 显式登记。先建立函数树，再按从外到内的顺序绑定；接口校验词法归属，若目标也是共享引用，则直接关联最终拥有者并标记其 shared_by_nested。同名局部变量不会自动成为共享变量。

自动捕获分析尚未接入，当前继续保留 mem2reg 对嵌套函数的原有保守限制。文本读写可由声明指令恢复全局、持久标记；共享引用尚未持久化，不能假设文本往返保留手动登记的共享关系。


## 第四部分：实现状态与相关文档

已实现：RecordInst、签名参数 Value、跨阶段映射、SlotInfo 声明与显式共享关系，以及 workspace_barrier 和两种 load 形式的指令与读写。mem2reg 已支持按需定义查询、占位 PHI、屏障定义传播和可能未定义的读取。

待实现：共享关系的自动捕获分析与持久化、运行时工作区接口、定义检查执行、clear 绑定有效性检查、延迟恢复计划及实际回退。mem2reg 对未受同块紧邻后继屏障保护的动态操作仍保守跳过。

### 运行时接入与验证

下一步先明确帧绑定和统一工作区访问接口，再接入实际工作区修改入口、正常返回切换与延迟恢复计划，最后完善异常恢复。自动共享捕获、脚本和共享工作区按实际支持范围接入。

验证需覆盖：分支与循环赋值、未绑定路径、赋值失败、clear 后重绑定、静态 load 覆盖或新增变量、重复访问暂停帧、部分修改后抛错、参数与多结果、隐藏迭代状态，以及编号压缩、来源保留和恢复计划的版本隔离。
